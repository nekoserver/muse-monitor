# SPEC.muse-monitor.security.hardening

## 目的と範囲

対象は muse-monitor Worker の認証・鍵まわり、その相手である receiver（muse-vm :8090）の照合、MonitorGateway Durable Object（DO）の状態と復旧、ダッシュボードの状態表示である。

結論（should-be）: 鍵は経路ごとに1つずつ分離し、receiver は Bearer を照合し、HMAC 署名は1回だけ受理し、認証判定は構造化ログに残し、DO の状態は使い捨てとして扱い、故障の理由とログイン状態は鍵なしで読める形で出さなければならない。2箇所に置く鍵（receiver 鍵）は検証する側（receiver）を正とし、提示側はそれに合わせ、不一致は両端の指紋で切り分けなければならない。登録が消えたノードの復旧は、状態を破棄せず対話ログインで再登録しなければならない。ローテーションは、receiver 側で新旧を重ねて受け付ける期間（オーバーラップ）を設けて行い、合わせ込みの間も監視を止めてはならない。2026-11-16 に移行はこの形で完了した（実施記録の節を参照）。本 SPEC は、完了した形の維持と、今後の変更の進め方を定める。

## 用語

- 参加鍵: WASM ノードが tailnet に参加するための鍵。Tailscale が発行する。
- receiver 鍵: receiver が Bearer として照合する値。運用者が決める任意文字列。
- 経路: 認証の単位となる入口。`/api/*`（ダッシュボード）、`/api/hmac/*`（本体 Worker）、DO→receiver、ノード→tailnet の4つ。
- 台帳: 鍵の一覧と属性を記録する文書（`docs/KEY_LEDGER.md`）。
- 復帰先: 変更を中止したときに最後に戻る、実経路で動作確認できた状態。

## 要求

### 高: receiver 側照合

- REQ-SEC-001: receiver は `/monitor/*` と `/queue` で `Authorization: Bearer <receiver 鍵>` を照合しなければならない。対象: T4。
- REQ-SEC-002: 照合は定数時間比較（`hmac.compare_digest`）で行わなければならない。receiver に鍵が未設定なら 503、不一致なら 401 を返さなければならない。対象: T4。

### 高: 鍵の役割分離と台帳化

- REQ-SEC-003: 鍵の役割は次表のとおり分離しなければならない。1つの鍵を別の役割に流用してはならない。対象: T1、T2。
  - `TS_AUTHKEY`: 発行者は Tailscale。WASM ノードの tailnet 参加専用。
  - `TS_API_KEY`: 発行者は運用者（任意文字列）。receiver への Bearer 専用。正は receiver の鍵ファイル（`~/.config/muse-receiver.env`）であり、Worker のシークレットはそこから配られた写しである（前提 P15、REQ-SEC-059）。
  - `WORKER_API_KEY`: 発行者は運用者。`/api/*` の Bearer とログイン Cookie の署名専用。
  - `MONITOR_HMAC_SECRET`: 発行者は運用者。本体 Worker との HMAC 署名専用。
- REQ-SEC-004: receiver が受け付ける鍵名は `TS_API_KEY` のみでなければならない。`TS_AUTHKEY` を receiver 鍵として扱ってはならない。対象: T4。
- REQ-SEC-005: 移行フォールバックは置いてはならない。`TS_API_KEY` をノードの参加に使ってはならず、参加に使う鍵の出所は `authKeySource` として `/api/status` と `/health` に常に出さなければならない。移行期間中だけ存在したフォールバックは 2026-11-16 に削除済みである。対象: T2。
- REQ-SEC-006: `TS_API_KEY` が未設定なら、receiver 呼び出しは `TS_AUTHKEY` の有無にかかわらず `receiver_key_missing` で失敗しなければならない。対象: T2。
- REQ-SEC-007: 台帳（`docs/KEY_LEDGER.md`）は、コードが読む全シークレットについて、名前・発行者・用途・消費側・設定場所・ローテーション手順・状態を記載しなければならない。鍵の値そのものを台帳に書いてはならない。対象: T3。
- REQ-SEC-008: 台帳の名前集合が、Env 宣言のシークレット名の集合および `wrangler.toml` のコメントに現れる名前の集合と一致しなければならない。対象: T3。

### 高: 経路別鍵

- REQ-SEC-009: 各経路はその経路専用の鍵で認証しなければならない。`/api/*` は `WORKER_API_KEY`（またはそれが発行する Cookie）、`/api/hmac/*` は `MONITOR_HMAC_SECRET`、DO→receiver は `TS_API_KEY`、ノード→tailnet は `TS_AUTHKEY`。対象: T1、T2。
- REQ-SEC-010: ある経路の鍵が別の経路で通ってはならない。対象: T1、T2。

### 高: 参加の確立は一度だけ

- REQ-SEC-021: ノードの永続化状態が存在する場合は、その状態から復帰しなければならない。認証キーをノードの生成に渡してはならず、login を呼んではならない。鍵の変更や不良で、参加済みのノードを壊してはならない。対象: T2。
- REQ-SEC-022: 永続化状態から復帰したノードが NeedsLogin を返した場合に限り、認証キーで login を1回だけ呼んでよい。対象: T2。
- REQ-SEC-023: 永続化状態が存在しない場合に限り、起動時に認証キーで login を呼ぶ（初回参加）。対象: T2。

### 中止条件と前提の検証（全ての変更に適用）

- REQ-SEC-024: 実経路の確認（AC-SEC-007）が通らない変更は、実装・移行を中止しなければならない。テスト（偽物の相手）が通っていることは、中止の解除理由にならない。対象: T1〜T4。
- REQ-SEC-025: 移行手順には、中止条件と復帰先（最後に実経路で動作確認できた状態）を、実施前に書かなければならない。復帰先が定義されていない移行を開始してはならない。対象: T3（本 SPEC の手順）。
- REQ-SEC-035: 前提節に検証状態が「未確認」の前提が残っている間は、その前提に依拠する変更を開始してはならない。実経路の結果が前提と食い違う兆候が出た場合は、変更を止めて前提の確認を先に行わなければならない。対象: T1〜T4。

### DO の復旧

- REQ-SEC-026: 永続化状態が原因でノードが起動しない場合（start の失敗が記録される、または状態が NoState のまま制限時間を超え NeedsLogin もログイン URL も出ない場合）、DO は永続化状態を破棄し、認証キーで初回参加をやり直さなければならない。復旧は他の全ての作業に先立って行う。対象: T2。
- REQ-SEC-027: 復旧のやり直しは1回だけとしなければならない。やり直しても Running にならない場合は、それ以上繰り返さず、失敗として状態に出さなければならない。対象: T2。
- REQ-SEC-028: 復旧で状態を破棄した場合は、その旨と理由を lastError に記録しなければならない（鍵の値は記録しない）。対象: T2。

### 影響の局所化

- REQ-SEC-029: シークレットの変更・削除・期限切れが、確立済みの参加と動作中のノードに影響してはならない。認証キーが効くのは、初回参加と、状態がログインを要求した瞬間だけとする。対象: T2。
- REQ-SEC-030: 永続化状態はキャッシュとして扱い、破棄と再参加で常に復旧可能でなければならない。状態の喪失そのものを障害として扱ってはならない。対象: T2。
- REQ-SEC-031: ノードの故障理由は、秘密を含まない要約として `/health` の公開状態に含めなければならない。要約は長さを制限し、URL・鍵の値・IP アドレスを含めてはならない。対象: T1、T2。
- REQ-SEC-032: 台帳に `TS_AUTHKEY` の期限日を記録しなければならない。永続化状態が有効な間は、参加キーが期限切れでもノードは止まってはならない。対象: T2、T3。
- REQ-SEC-033: 永続化状態は、ノードの起動に使う前に、構造の完全性（オブジェクトであり、全ての値が文字列であること）を検証しなければならない。検証に失敗した状態で起動を試みてはならず、破棄して認証キーで再参加しなければならない。構造は健全でも意味的に壊れた状態は、REQ-SEC-026 の復旧が受け持つ。対象: T2。
- REQ-SEC-036: 【版21で廃止】永続化状態から復帰したノードが NeedsLogin のまま対話ログイン URL を提示して制限時間を超えた場合に、状態を破棄して認証キーで再参加する要求であった。revision 16 の実経路で悪化した（破棄後の再参加が完了せず、登録が control に届かなかった）ため保留となり、2026-11-21 に REQ-SEC-058（状態を破棄しない対話ログインへの切り替え）が実経路で復旧を確認したことにより、本要求は REQ-SEC-058 に置き換えて廃止する。再開してはならない。対象: T2。
- REQ-SEC-037: ライブ表示ページ（Static Assets の `live.html`）から、全 section の出力を WebSocket で定期的に受信して表示できなければならない。配信は `GET /api/live` の upgrade とし、認証は既存の Bearer 鍵またはログイン Cookie を upgrade の前に検証しなければならない（新しい秘密を追加しない。未認証は 401 で upgrade しない）。取得は接続がある間だけ DO の alarm で行い（間隔 10 秒）、接続が無ければ section を取得してはならない。ノードが Running でない間は、section ではなくノードの状態を frame として配信し、接続は維持しなければならない。前提: DO の hibernation（acceptWebSocket と alarm）は eviction を跨いで接続と定期実行を保つ（未実測。デプロイ後の実経路で確認する）。対象: T1。
- REQ-SEC-038: ダッシュボードのキー登録ボタンは、ブラウザの実際のログイン状態を反映しなければならない。初期表示は「キー登録」とし、ページ読み込み時に Cookie のみ（キーを送らず）で認証状態を確かめて、ログイン中であれば「ログアウト」に切り替えなければならない。キー登録が成功したら「ログアウト」に切り替え、ログアウトしたら「キー登録」に戻さなければならない。データ取得が 401 になった場合（Cookie の期限切れ等）も「キー登録」に戻さなければならない。対象: T1。
- REQ-SEC-039: ダッシュボードは、2段階の状態を分けて表示しなければならない。第1段階はこのブラウザのキー認証（認証済み／未認証）、第2段階はノードのログイン状態であり、別々の行でそれぞれの状態が分かること。第1段階だけが解除された状態（キー認証は済んだがノードは未ログイン）が、全体が失敗したように見えてはならない。対象: T1。
- REQ-SEC-040: ダッシュボードで未認証の間は、キー入力窓より下のエリア全体を押せなくしなければならない。そのエリアは一つのセクション（コンテナ要素）として括り、グレーアウト処理はボタン個別ではなくそのセクション全体に適用すること。認証済みになれば操作できるようになり、ログアウトした直後にも即座にその状態へ移行しなければならない。キー登録ボタン自体は常に押せること。対象: T1。
- REQ-SEC-041: 未認証の間のグレーアウトは、透明度を下げるだけでなく彩度も落とさなければならない（filter による grayscale 化）。領域内の文字色・ボタン色が色として目立ったまま残ってはならない。認証済みになれば色は即座に戻らなければならない。対象: T1。
- REQ-SEC-042: ノードが対話ログイン待ちでログイン URL が存在する間、ダッシュボードはキー認証済みの表示において、その URL へのリンクをノードのログイン状態表示の近くに提示し、運用者がページからログイン承認へ進めるようにしなければならない。ログイン URL は鍵なし経路（/health）に出してはならない（REQ-SEC-031 を維持する）。ノードが Running になるか URL が無くなれば、リンクは消えなければならない。対象: T1。
- REQ-SEC-043: 鍵なし /health のノード情報とダッシュボードのログイン状態表示は、ノード自身の Tailscale IPv4（自ノードの netmap の addresses から得る）を含まなければならない（出典: 2026-11-18、Okiraku の指示「node-monitor の破損チェックも本体同様に実際の IP のヘルスチェック状態が修復後に変わり画面上でも確認できるように」）。ダッシュボードはその IP をログイン状態の表示に併記し、色は既存の規則（Running = 緑、それ以外 = 赤）に従わなければならない。これにより、状態破棄と再参加による修復の前後で、IP の変化と色の変化を画面上で確認できる。出すのは自ノードの住所だけであり、受信側など他ノードの IP、ログイン URL、鍵の値は従来どおり出してはならない（REQ-SEC-031 の、エラー文中の IP を伏せる規則も維持する）。未参加で住所が無いときは、その旨（未割当）が分かる表示にしなければならない。対象: T1。
- REQ-SEC-044: ノードの起動試行は、1回ごとに DO ストレージへ記録しなければならない（出典: 2026-11-18、Okiraku の承認。本体ワーカーの起動ログ（tailscale_wasm_boot_log）と同種の記録をモニタにも入れる）。記録は試行の開始時点で書き始め、状態遷移のたびと終了時に、メモリ上の状態 Map の非同期 flush を経由せず直接ストレージへ書かなければならない（前提 P1・P2: evict で証拠自体が消えるため）。各記録には、開始時刻、起点（状態なしの新規か、永続化状態からの復帰か）、login の呼び方（生成直後か、NeedsLogin での繰り延べか、呼ばなかったか）、観測した状態遷移（状態と経過ミリ秒）、対話ログイン URL の提示があったかどうか（URL 自体は書かない）、結果（Running 到達、時間切れ、エラー、中断）、エラーの要約（長さ上限付き）を含めなければならない。結果が記録されないまま次回の読み込みを迎えた記録は、「中断」として確定させなければならない（前回の試行が途中で切れた証拠になる）。状態の破棄（epoch リセット、整合性チェック不合格、復旧のための破棄）が起きたときは、その理由を同じ記録列に残さなければならない。記録は上限50件とし、古いものから落とす。記録の書き込みに失敗しても、ノードの起動を妨げてはならない。鍵の値を記録に含めてはならない。新しい環境変数・シークレット・設定スイッチを足してはならない。対象: T2。
- REQ-SEC-045: 起動記録は、鍵なし /public-status のノード情報に直近5件まで含めて出さなければならない（lastError と同格の情報として扱う。ログイン URL と鍵の値は含めない）。認証済みの /api/status には直近20件まで含めなければならない。ダッシュボードのログイン状態の表示には、直近の起動試行（時刻・起点・結果）を併記し、NeedsLogin のまま終わった試行が続いていることと、「中断」の記録があることを、画面で見えるようにしなければならない。対象: T1、T2。
### 時間ごとの記録・モード設定・自動復旧・DDoS 耐性（版19）

- REQ-SEC-046: DO は1時間ごとに、ノードの状態をサンプルとして DO ストレージへ記録しなければならない（出典: 2026-11-18、Okiraku の指示「そのページの最上部にヘルスチェック結果の時間ごとチャートでも表示できれば」および「チャートも今回のSPECに入れる」）。サンプルには、時刻、ノードの状態（未起動を含む）、直近の起動試行の結果、自ノードの IP を含めなければならない。サンプルは上限168件（7日分）とし、古いものから落とす。サンプルのために永続化状態を破棄してはならない。サンプル時刻にノードが未起動なら、既存の読み取り経路と同じくバックグラウンドで起動を開始してよい。サンプルの記録に失敗しても、他の動作を妨げてはならない。新しい環境変数・シークレットを足してはならない。対象: T2。
- REQ-SEC-047: 【版21で廃止】ダッシュボードの設定で「手動」「自動」のモードを選び、自動復旧（REQ-SEC-048 の状態破棄）の発動を切り替える要求であった。版21で REQ-SEC-048 の破棄機構が REQ-SEC-058（状態を破棄しない対話ログインへの切り替え）に置き換わり、切り替え先の対話ログインは状態を破壊せず承認も利用者の手に残るため、発動をゲートするモードは不要となった。モード設定を実装してはならない。対象: T1、T2。
- REQ-SEC-048: 【版21で廃止】モードが「自動」のときに限り、前提 P8 の固着で永続化状態を破棄して再参加する要求であった。破棄と再参加の機構は REQ-SEC-058 に置き換えて廃止する。再開してはならない。前提 P11（状態の指紋）は、本要求の廃止により参照を失うが、記録として残す。対象: T2。
- REQ-SEC-049: ダッシュボードの最上部に、REQ-SEC-046 のサンプルを時間ごとの系列として表示するチャートを置かなければならない。チャートの各点からは、その時間帯のサンプルと起動記録（異常の検知時刻と、それに対応する復旧の記録を含む）を呼び出して表示できなければならない（出典: 2026-11-18、Okiraku の指示「異常を検知した時間とそれに対応して自動復旧させた記録もチャート上から呼び出せるように」）。チャートのデータは鍵なし経路（`/health` と同格）で読み取り専用に出してよいが、ログイン URL と鍵の値は含めてはならない。対象: T1、T2。
- REQ-SEC-050: 起動試行が時間切れまたはエラーで終わった後5分間は、鍵なし経路からの読み取りをきっかけに新しい起動試行を始めてはならない（出典: セキュリティ監査の確定所見1「鍵なし /health が失敗し続けるノード起動をクールダウンなしに繰り返す」と、2026-11-18 の Okiraku 指示「DDoS耐性もつけといて」）。クールダウン中も、公開状態は最後に分かった状態で返さなければならない。認証済み経路の取得、REQ-SEC-046 のサンプル時刻の起動は、このクールダウンの対象外とする（それぞれ頻度が有界であるため）。版21の例外として、REQ-SEC-058 の対話ログインへの切り替えは、DO インスタンスごとに1回に限り鍵なし経路から駆動してよい（状態を破棄せず、鍵も提示せず、承認は利用者の手に残るため）。対象: T1、T2。
- REQ-SEC-051: 鍵なし経路（`/health` とチャート用データ）は、1回の要求で section の取得や receiver への問い合わせを行ってはならず、応答の大きさは記録の上限（サンプル168件、起動記録50件）で有界でなければならない。鍵なし経路は読み取り専用とし、起動記録とサンプル以外の書き込みを引き起こしてはならない。対象: T1、T2。
- REQ-SEC-052: ライブ表示の WebSocket でクライアントから "refresh" が届いても、掃引は REQ-SEC-037 の間隔（10秒）ごとに最大1回までとし、メッセージの数だけ掃引を繰り返してはならない（出典: セキュリティ監査の確定所見3「"refresh" が無制限に16セクションの掃引を引き起こす」）。対象: T2。

- 本改訂（版18）では、復旧の発動条件（REQ-SEC-026〜028、036）は変更しない。前提 P8 の固着（URL の提示がない NeedsLogin の時間切れ）を復旧対象に広げるかどうかは、REQ-SEC-044 の記録で固着の段階（鍵が提示されたか、遷移がどこで止まるか、試行が途中で切れていないか）が確定してから、別の改訂で判断する。URL の提示がない NeedsLogin は、control 側の応答が遅いだけの場合もありうるため、証拠なしに状態を破棄する対象へ広げてはならない。
- 本改訂（版19）では、復旧対象の拡大は REQ-SEC-047 のモード設定で「自動」が選ばれた場合に限り、REQ-SEC-048 の条件（指紋ごとに1回限り）で有効になる。初期値の「手動」では版18と同一の振る舞いであり、デプロイ自体では復旧の条件は変わらない。復帰先は revision 24（版17 のデプロイ）であり、戻しは PR の revert で足りる（版19の記録と設定は追加のストレージキーであり、既存の状態キーには触れない）。

### ページ読み込み時のノード確認と手動ボタン（版20）

- REQ-SEC-053: 認証済み `/status` の取得のたびに、DO はノードの確認を行わなければならない（出典: 2026-11-18 の Okiraku の指示「そのmuse-monitorのページ読み込み時にでも毎回チェックを」。前提 P12）。ノードが Running でなく、この DO インスタンスで開いている起動試行（結果が未確定の REQ-SEC-044 の記録）がない場合、DO はバックグラウンドで新しい試行を駆動しなければならない（ノード未生成なら通常の起動、生成済みで Running でないなら REQ-SEC-054 の再駆動）。`/status` の応答は現在の状態で即時に返し、試行の完了を待ってはならない。鍵なし経路（`/health`）はこの確認の契機にしてはならない（REQ-SEC-050 の方針）。ただし REQ-SEC-058 の対話ログインへの切り替えは、REQ-SEC-050 の例外として、DO インスタンスごとに1回に限り鍵なし経路から駆動してよい。新しい環境変数・シークレット・設定スイッチを足してはならない。対象: T2。
- REQ-SEC-054: 再駆動は、残っているノードに対して login() を呼び直し、新しい起動記録を REQ-SEC-044 の記録列に開くことでなければならない（起点は persisted、login の呼び方は deferred として記録する）。login() に渡す鍵は REQ-SEC-058 の規則で選ばなければならない（直前の試行が固着の形なら鍵なし、それ以外で認証キーが設定されていればその値、設定されていなければ対話ログイン）。開いている試行がある間の確認では、login() を重ねて呼んではならず、記録も重ねて開いてはならない。再駆動は永続化状態を破棄してはならない（状態の破棄は REQ-SEC-026〜028、REQ-SEC-033 の条件でのみ行う）。対象: T2。
- REQ-SEC-055: `/status` が返す loginUrl は、開いている試行の中で提示された URL のみでなければならない。試行が Running 以外の結果で閉じた時点で、その試行が提示した URL は以後返してはならない。開いている試行がないときに届いた URL の通知は採用してはならない（前提 P13）。鍵なし経路に URL を出さない従来の規則（REQ-SEC-018、REQ-SEC-042）は変えない。対象: T1、T2。
- REQ-SEC-056: ダッシュボードに、ノードの再確認を手動で駆動するボタンを置かなければならない（出典: 2026-11-18 の Okiraku の指示「手動ボタンも」）。ボタンは認証済み `POST /api/node-check` を呼び、Worker は DO へ転送し、DO は REQ-SEC-053 と同じ確認を即時に駆動して（駆動の判断を応答の後に延ばさない）現在のノード状態を返さなければならない。未認証の呼び出しは他の `/api/*` と同じ規則で拒否し、認証判定は REQ-SEC-014 の監査ログに残さなければならない。対象: T1、T2。
- REQ-SEC-057: 永続化状態が有効な場合、新しい DO インスタンスは login() を呼ばずに Running へ復帰できなければならない（既存の振る舞いをテストで固定する。復帰に利用者の対話ログイン承認を要してはならない）。対象: T2。
- 本改訂（版20）の復帰先は revision 25（版18 のデプロイ、PR #17 マージ時点の main）であり、戻しは PR の revert で足りる（起動記録の形式は変えず、追加のストレージキーも作らない）。

### 対話ログインへの切り替えと receiver 鍵の正（版21）

- REQ-SEC-058: 直近の起動試行が前提 P8 の固着の形（結果が時間切れ、対話ログイン URL の提示がなく、最後の状態遷移が NeedsLogin）で閉じた場合、DO は次の起動または再駆動で、同じノードに対して鍵を付けずに login() を呼び、対話ログイン URL の発行を求めなければならない。この切り替えで永続化状態を破棄してはならない。切り替えを行った試行は、起動記録にその旨を残さなければならない。発行された URL の提示範囲は REQ-SEC-055 と REQ-SEC-042 の規則に従う（認証済み経路のみ）。対話ログインのリンクが時間切れになった場合は、認証済みの再確認で鍵なし login() を呼び直し、新しいリンクを発行してよい。復旧の判定は、ノードが Running になり receiver が解決できた時点とする。出典: 2026-11-21 の実経路（revision 30 で対話ログインの承認が成功し復旧した。PR #21 で実装）と、同日の Okiraku の指示（そもそもの設計を明確にした上で SPEC とテストを書き直すこと）。本要求は REQ-SEC-036 と REQ-SEC-048 を置き換える。対象: T2。
- REQ-SEC-059: receiver 鍵（`TS_API_KEY`）の正は receiver 側の鍵ファイルでなければならない（前提 P15）。Worker のシークレットは、receiver 側の値から配られた写しとして扱わなければならない。発行とローテーションは次の順序で行わなければならない。(1) receiver 側の鍵ファイルに新しい値を `TS_API_KEY` として置き、旧値を REQ-SEC-063 のオーバーラップ（`TS_API_KEY_PREVIOUS` と期限）として残す。receiver が読み直したことを `/health` の指紋で確認する。(2) Worker のシークレットに新しい値を設定する。(3) 両端の指紋の一致と、section の実読み取り1件で確認する。確認できたら旧値の行は削除してよい（削除しない場合は期限で失効する）。台帳（`docs/KEY_LEDGER.md`）の `TS_API_KEY` のローテーション欄はこの順序を記載しなければならず、ローテーション記録には実施日と新旧両方の指紋と確認結果を記録しなければならない。オーバーラップを伴わない差し替え（旧値を残さずに receiver を先に変えること、および receiver より先に Worker を変えること）をしてはならない。オーバーラップの期間中は、どちらの側の値を戻しても照合は壊れないため、ロールバックは鍵ファイルの書き戻しで足りる。対象: T2、T3。
- REQ-SEC-060: 鍵の指紋は、鍵の値の SHA-256 ハッシュ（16進文字列）の先頭8文字と定義する。指紋は鍵の値そのものではないため、照合のために出してよい。receiver は `/health` の応答に `keyFingerprint` を含めなければならない（鍵が未設定の場合は null としなければならない）。receiver は 401 の応答本文に `expectedKeyFingerprint`（receiver 側の鍵の指紋）と `presentedKeyFingerprint`（提示された Bearer の指紋。Bearer が無い場合は null）を含めなければならない。MonitorGateway は、自らが提示する receiver 鍵の指紋を計算し、認証済み `/status` の応答に `receiverKeyFingerprint` として含めなければならない。鍵なし経路（`/public-status` と `/health`）に receiver 鍵の指紋を出してはならない（運用者が弱い値を選んだ場合に、提示側の指紋が推測の照合材料になるため）。鍵の値を、指紋を出す面のいずれにも含めてはならない。対象: T2、T4。
- REQ-SEC-061: receiver が 401 を返した場合、MonitorGateway は `receiver_unauthorized`（HTTP 502、`upstreamStatus: 401`）を返し、その本文に、自ら計算した `presentedKeyFingerprint` と、receiver の応答本文から得た `expectedKeyFingerprint`（receiver が指紋を返さない場合は null）を含めなければならない。本文のメッセージは、正が receiver 側であることと、合わせる操作（Worker のシークレット `TS_API_KEY` を receiver 側の値に合わせること）を明示しなければならない。401 に対して、別の鍵での再試行と、ノードの状態変更を行ってはならない。ダッシュボードはこのエラーをブラウザ認証の失敗と区別して表示し、ブラウザの認証表示と操作可否を維持しなければならない。対象: T1、T2。
- REQ-SEC-062: receiver 側に鍵が未設定であることを表すエラー名は `receiver_key_not_configured` に統一しなければならない。receiver の 503 応答本文、MonitorGateway の 503 の変換、契約文書（`docs/RECEIVER.md` と lib の `SPEC.scripts.md`）は、この名前を用いなければならない。MonitorGateway 自身に `TS_API_KEY` が未設定の場合のエラー名は `receiver_key_missing` とし（REQ-SEC-006）、両者を混用してはならない。対象: T2、T4。
- REQ-SEC-063: receiver は、鍵ファイルに `TS_API_KEY_PREVIOUS`（旧値）と `TS_API_KEY_PREVIOUS_UNTIL`（期限、UNIX epoch 秒）が両方ある場合に限り、期限が切れるまで旧値の Bearer を、現在の値と同じ経路で受け付けなければならない。期限を過ぎた旧値は、現在の値と一致しない提示として 401 で拒否しなければならない（その際の指紋の扱いは REQ-SEC-060 に従う）。`TS_API_KEY_PREVIOUS_UNTIL` が無い、または整数として解釈できない場合は、旧値を受け付けてはならない。オーバーラップの既定の長さは24時間とし、鍵ファイルに期限を書く時点で確定しなければならない（受け付けの判定に相対時間を用いてはならない）。対象: T4。
- REQ-SEC-064: receiver は、gated な要求ごとに鍵ファイルの更新時刻を確認し、変わっていれば読み直さなければならない（再起動を要しない）。読み直した結果が鍵なしになった場合は、REQ-SEC-020 のとおり未設定として扱い 503 を返さなければならない（直前の値で通し続けてはならない）。対象: T4。
- REQ-SEC-065: receiver は、オーバーラップの間、`/health` の応答に `previousKeyFingerprint`（旧値の指紋）と `previousKeyUntil`（期限、UNIX epoch 秒）を含めなければならない。オーバーラップが無い場合は、両方とも null としなければならない。旧値で受理した場合は、その旨を receiver のログに記録しなければならない（鍵の値は記録せず、提示された指紋で記録する）。対象: T4。
- REQ-SEC-066: `/api/hmac/*` の署名は、経路に束縛しなければならない。署名の材料は `<UNIX秒>.<経路>.<section>` とし、経路は要求パスそのもの（`/api/hmac/status` または `/api/hmac/monitor/<section>`）とする。検証側は、提示された署名を、その要求の経路で計算した値とだけ照合しなければならない。別の経路のために作られた署名は、section が同じでも受理してはならない（出典: セキュリティ監査の確定所見2。テレメトリの section `status` 用の署名が、ログイン URL を含む `/api/hmac/status` を開いていた）。使い捨ての claim は（経路、署名）の組を単位としなければならない。鍵（`MONITOR_HMAC_SECRET`）の値・発行・保管場所は本要件では変更しない。対象: T1、T3。
- REQ-SEC-067: REQ-SEC-066 への移行は、次の順序で行わなければならない。(1) 検証側（muse-monitor）が、`/api/hmac/monitor/*` では旧形式（`<UNIX秒>.<section>`）と新形式の両方を受け付け、`/api/hmac/status` では新形式だけを受け付ける状態にする。(2) 署名側（本体 Worker）が、全ての経路で新形式の署名を出すようにする。(3) 両側のデプロイが実経路で確認できたら、検証側は旧形式の受け付けを廃止する。(1) の状態では、本体 Worker の `/api/hmac/status` 取得は (2) のデプロイまで 401 になる（テレメトリの取得は影響を受けない）。この一時的な不整合は移行の仕様として許容し、隠してはならない。旧形式の受け付けを残したまま、移行を完了として扱ってはならない。対象: T1、T3。
- 本改訂（版21）の復帰先は revision 34（PR #22 マージ時点の main）であり、2026-11-21 に実経路で node が Running、receiverResolved が true であることを確認済みである。戻しは PR の revert で足りる。本改訂は SPEC とテストの書き直しであり、実装の変更を含まない。REQ-SEC-060〜062 の実装（receiver.py の指紋と 503 のエラー名、MonitorGateway の指紋の露出）は次の変更であり、テストは実装に先行して失敗する形で用意されている。


### 状態の表示

- REQ-SEC-034: ダッシュボード（`/`）は、ノードのログイン状態を色分けした文字で明示しなければならない。ノードが Running の場合は「ログイン中」と分かる表示を、それ以外の場合は「未ログイン」と分かる表示を、色だけに頼らず文字でも判別できる形で出さなければならない。対象: T1。
- REQ-SEC-018: `/health` とダッシュボード HTML（`/`）は無認証でなければならない。`/health` が返す公開状態には、鍵の出所名は含めてよいが、鍵の値・ログイン URL・IP アドレスを含めてはならない。対象: T1、T2。

### 中: 署名付き要求とリプレイ防止

- REQ-SEC-011: HMAC 署名（hex 文字列そのもの）は、その有効窓（±300 秒）の内側で最大1回だけ受理しなければならない。再使用は 401 `{"error":"replay"}` で拒否しなければならない。対象: T1、T2。
- REQ-SEC-012: 受理記録は MonitorGateway DO のストレージに署名とタイムスタンプで保持し、2×窓より古い記録は削除しなければならない。対象: T2。
- REQ-SEC-013: 受理記録の確認ができない場合（DO のエラー）は、要求を 503 `{"error":"replay_check_unavailable"}` で拒否しなければならない（fail-closed）。対象: T1。

### 中: 構造化監査ログ

- REQ-SEC-014: `/api/*` と `/api/hmac/*` の認証判定は、1件ごとに JSON 1行のログを出さなければならない。形式は `{"type":"audit","ts":<ISO 8601>,"route":<path>,"auth":"bearer"|"cookie"|"hmac"|"none","result":"accepted"|"rejected"|"replay"|"unavailable","section":<任意>}` とする。対象: T1。
- REQ-SEC-015: 監査ログに鍵の値・Cookie の値・署名そのものを含めてはならない。対象: T1。

### 低: ローテーションとアラート

- REQ-SEC-016: 台帳に各鍵のローテーション手順と最終実施日の記録欄を持たなければならない。コード側の自動ローテーションは実装しない。新旧併用の受理期間は、`TS_API_KEY` の手動ローテーションに限り REQ-SEC-063 の形で receiver が持たなければならない。それ以外の鍵に新旧併用の受理期間を持たせてはならない。`WORKER_API_KEY` を変えると既存のログイン Cookie は全て無効になることを台帳に明記しなければならない。対象: T3。
- REQ-SEC-017: アラートの自動通知はこの Worker には実装しない。検出面は `/health` の公開状態と muse-vm 側の receiver-watch が担う分担を、台帳に記録しなければならない。対象: T3。

## 例外・禁止事項

- REQ-SEC-019: HMAC の同一ヘッダ集合を同じ秒に再送する正当なリトライは、REQ-SEC-011 によりリプレイとして拒否される。これは誤判定として許容する。対象: T1。
- REQ-SEC-020: receiver の鍵ファイルが読めない場合は未設定として扱い、503 を返さなければならない。無認証で素通ししてはならない。対象: T4。
- 鍵の値を、チャット・台帳・ログ・監査ログのいずれにも書いてはならない。
- receiver 鍵の値を `TS_AUTHKEY` に設定してはならない（2026-11-12 の障害の再発防止）。
- REQ-SEC-054 の再駆動による login() の呼び直しは、直前のセッションで承認手続き中の利用者の承認を無効化しうる（前提 P13）。この場合、利用者は現在の試行が提示する新しい URL から承認し直すものとする。画面が常に現在の試行の URL のみを出す（REQ-SEC-055）ため、承認の行き先は一意に定まる。これは誤判定として許容する。
- REQ-SEC-053 の確認の駆動が失敗しても（login() の例外を含む）、`/status` の応答は最後に分かった状態で返さなければならない。確認の失敗を応答のエラーにしてはならない。

### 実測した現状（2026-11-21、HMAC 経路。PR #33・本体 PR #2706 のマージ前）

`/api/hmac/*` の現状の仕様は次のとおりである（本体 Worker の `src/utils/museMonitor.ts` と muse-monitor の `src/index.ts`・`src/do.ts` の現行コードから実測）。

- 経路の使い分けは、呼び出し側が section 名で決める。`status` の場合は `GET /api/hmac/status`（DO の `/status`。MonitorGateway 自身の状態を返し、ログイン待ちの間は `loginUrl` と `browseUrl` を含む）。それ以外の場合は `GET /api/hmac/monitor/<section>`（DO の `/monitor/<section>`。receiver の section 本文を中継する）。
- 検証側（DO）の section の集合は16個である（`status`、`diag`、`jobs`、`pkgs`、`vm`、`procs`、`ports`、`git`、`recent`、`pending`、`execlog`、`sdkhealth`、`sdkprofiles`、`sdksessions`、`sdkts`、`hooks`）。署名側の一覧は15個で `hooks` を含まないため、本体経由では `hooks` は呼ばれない（署名側で `unknown_section` になる）。
- 署名の現状の形: ヘッダ `X-Muse-Timestamp`（UNIX 秒）と `X-Muse-Signature` = hex HMAC-SHA256（`MONITOR_HMAC_SECRET`、`"<ts>.<section>"`）。受理窓は ±300 秒。**署名に経路が含まれない**ため、section `status` の署名は上記2経路のどちらでも照合が通る。これが監査所見2の現状であり、REQ-SEC-066 が変える対象である。
- 使い捨て: 照合が通った署名は DO の `/hmac-claim` で署名そのものを単位に claim し、再提示は 401 `{error: "replay"}` になる。claim を確認できない場合は 503 `{error: "replay_check_unavailable"}` で fail-closed にする。照合の失敗は 401 `{error: "unauthorized"}` である。
- 監査: 判定ごとに構造化ログを1行出す（`route`、`auth: "hmac"`、`decision`、`detail` = section）。
- 鍵: `MONITOR_HMAC_SECRET` は本体 Worker と muse-monitor の両側に同じ値を運用者が設定する。Worker のシークレットは write-only であり、どちらの側からも値を読み出す手段はない。
- 移行の実施計画（PR の対応、デプロイの順序、デプロイ後の確認、旧形式の廃止の進め方）は、構想・計画レベルの内容として `PLAN.muse-monitor.hmac-route-binding.md` に置く。本 SPEC には置かない。
