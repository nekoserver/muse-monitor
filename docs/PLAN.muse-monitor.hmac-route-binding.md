# PLAN.muse-monitor.hmac-route-binding

HMAC 署名の経路束縛（監査所見2）の実施計画。要求そのものは SPEC 側（REQ-SEC-066・067）にあり、ここには構想・計画レベルの内容（PR の対応、デプロイの順序、確認の進め方、残作業）だけを置く。

## 現状

- 署名の材料は `<ts>.<section>` で経路を含まない。section `status` の署名が `/api/hmac/status`（ログイン URL を含む）と `/api/hmac/monitor/status`（テレメトリ）の両方で通る。現状の仕様の詳細は SPEC の参考記録「実測した現状（2026-11-21、HMAC 経路）」にある。

## 実施する PR

| 順 | PR | 内容 | 状態 |
|---|---|---|---|
| 1 | muse-monitor #33 | 検証側: 署名を `<ts>.<経路>.<section>` で照合。claim の単位を（経路、署名）に。移行期は monitor 経路で旧形式も受理し、`/api/hmac/status` では新形式のみ受理 | マージ済み 2026-11-21（main f3df09c。vitest 170/170、tsc クリーン） |
| 2 | 本体 Worker #2706 | 署名側: `signMuseMonitor` が送るパスで署名 | 作成済み（対象テスト 13/13、tsc エラー数ベースと同数） |

## デプロイの順序と、その間の影響

進捗（2026-11-21）: #33 がマージされた。現在は手順2（#2706 のマージ・デプロイ）待ちであり、この間 `/api/hmac/status` 取得が 401 になるのは想定どおりの状態である。

1. **#33 を先にマージ・デプロイする。**（済）この間、本体 Worker の `/api/hmac/status` 取得だけが 401 になる。テレメトリ取得は旧形式のまま通り、影響を受けない。
2. **#2706 を次にマージ・デプロイする。** これで全経路が新形式に揃う。
3. 逆順にすると、本体→monitor の取得が全て 401 になる（#33 のデプロイで回復する）。

マージとデプロイは Okiraku の手で行う。本体 Worker 側のデプロイは Workers Builds のビルド（7分以上）を伴うため、#2706 のマージ後はビルド結果を確認してから次に進む。

## デプロイ後の確認（実経路）

- 本体 Worker 経由のテレメトリ取得（例: section `jobs`）が成功すること
- 本体 Worker 経由のステータス取得（`/api/muse-monitor/status` 相当）が成功すること
- muse-monitor の監査ログに、移行期の 401（status 経路）が #2706 のデプロイ後に消えること

## 残作業（構想レベル）

- **旧形式の廃止**: 上記の実経路確認が済んだら、検証側で旧形式（`<ts>.<section>`）の受け付けを外す仕上げの PR を出す。それまでは移行は未完了として扱う（REQ-SEC-067 の (3)）。
- **`MONITOR_HMAC_SECRET` の正の所在**: 定めていない（SPEC 版22の EVAL の不足の継続）。定めるかどうかは Okiraku の判断で、期限は未定。本計画の対象外。

## ロールバック

- 移行の途中での戻しは順序を逆に辿る: 署名側（#2706）を revert してから検証側（#33）を revert する。
- #33 のみの状態で戻す場合は #33 の revert だけで足りる（テレメトリは旧形式で通っているため）。
- 鍵の値には一切触れないため、鍵のロールバックは不要である。
