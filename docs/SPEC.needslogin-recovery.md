# muse-monitor の Tailscale 再ログイン仕様

対象は、本体 Worker の監視機能がサービスバインディングで参照する `muse-monitor` の MonitorGateway。管理画面の認証と Tailscale ノードの参加は独立して判定する。

| 要件 | 判定条件と期待する動作 |
|---|---|
| 保存済みノードの復帰 | 保存状態が有効なら同じノードで復帰する。状態が `Running` ならログインし直さない。保存状態で `NeedsLogin` になったときだけログインを試みる。 |
| 承認リンクが発行されない固着 | `NeedsLogin` のまま60秒が経過し承認リンクも無かった試行を、保存済み起動記録から検出する。次の起動・再確認では鍵を付けずに同じノードの対話ログインを要求する。この条件で保存状態を破棄しない。 |
| 公開ヘルスと再試行 | 公開 `/health` は起動済みインスタンスの固着に対して、対話ログインへの切り替えを1インスタンスにつき1回だけ駆動できる。同時アクセスで再試行を重複させない。 |
| 承認リンクの取得と更新 | 承認リンクは認証済みのステータス応答だけに含める。起動記録と公開ヘルスでは発行の有無を返す。画面はログイン中に5秒ごとに状態を読み直す。対話ログインの期限が切れたら、認証済みの再確認で新しいリンクを再発行できる。 |
| 復旧判定 | 承認リンクが発行された時点は承認待ち。ノードが `Running` になり、`muse-vm` の受信側へ到達してから復旧と判定する。 |

## 検証

- `test/do.test.ts` では、60秒の固着記録を入れた新規インスタンスと、稼働中のインスタンスを検査する。保存状態の維持、対話ログインへの切り替え、公開応答の秘匿、期限切れ後のリンク再発行、承認後の受信側への到達を確認する。
- `test/index.test.ts` では、未認証の再確認が拒否されることと、画面が遅れて届くリンクを取り直すことを検査する。
- デプロイ時は [公開ヘルス](https://muse-monitor.nekoflare.workers.dev/health) で対象リビジョン、`node.node = Running`、`node.receiverResolved = true` を照合する。最後に認証済みの本体 Worker 経由で監視項目を1件読み取る。

障害時の手順は [RECOVERY.md](RECOVERY.md) を参照する。
